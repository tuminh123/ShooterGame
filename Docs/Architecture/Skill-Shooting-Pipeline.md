# Skill and shooting pipeline

See [Skill Run Progression](Skill-Run-Progression.md) for the current model.

SkillDataSO stores complete per-level behavior data and a separate ISkill template
list. Enum types pair the data with the behavior. Abstract Skill supplies default
lifecycle methods. SkillRuntime activates only behaviors with data at its level.
There is no ShootingLevelTable, root stat bonus, string behavior ID or wrapper entry.

ShootingData owns the shooter/movement/projectile settings for a single level.
ShootingSkill snapshots a volley, uses shared shooting/movement services and gives
projectiles independent damage/effect snapshots. The existing projectile/VFX
pipeline below remains in use.

## VFX child lifecycle

- `CombatAssets` has two shared shells: `ProjectileView.prefab` (formerly HolyBolt) and `EffectView.prefab` (formerly HolyImpact). Their original GUIDs are preserved. Bullet entries contain type, child visual prefab, impact effect and a per-type hit radius/offset; effect entries contain type and child visual prefab. Skills select BulletType; every skill/level using a type shares its catalog hitbox. `Tools > Shooter Game > Hitbox Editor` edits these entries independently. There are no catalog sprite, tint or width overrides.
- Projectile visuals live in `Prefabs/VisualProjectile`. The inactive shell rents the chosen visual child and restores its authored local transform. Release returns the child before the shell. Camera culling combines child Renderer bounds. ProjectileView does not control Animator, ParticleSystem or TrailRenderer playback; the visual prefab owns presentation. Author it facing local +X and configure color, size, animation and materials inside the prefab.
- The catalog maps Holy, Fire, Ice and Poison bullets to matching impact IDs; HolyImpact keeps serialized ID 1. FireImpact, IceImpact, PoisonImpact, LightningImpact and WindImpact have distinct entries. Added sample visuals currently reuse the original artwork with prefab-authored tints; replace these child prefabs with your own VFX. Prewarm prepares both shells and their children.

- Scripts are grouped in `Combat/Effects/Visuals`. The shared `EffectView` shell owns pooling and calls `IEffectVisual.Play()` / `StopAndReset()`. It subscribes to `Completed` before playback and releases the child before the shell when the visual finishes. There is no fixed duration or lifetime timer on the shell.
- `AnimationEffectVisual` implements `IEffectVisual` directly. Assign an `AnimationClip` on the visual prefab or call `SetVisual(clip)` before playback. An Animator is required on the same root; no AnimatorController is needed. A PlayableGraph plays the clip from time zero using gameplay time and the configured playback speed. Completion follows the actual playable time, so a long clip is not truncated by a shared shell duration. The graph is destroyed on cancellation, disable, destruction or replay.
- `ParticleEffectVisual` implements `IEffectVisual` directly. It plays the root ParticleSystem with children and waits for `IsAlive(true)` to become false, including delayed emission and remaining child particles. These pooled impact effects are forced to one-shot, gameplay-scaled playback with auto-destroy/disable disabled on every child system.
- Both implementations emit `Completed` once on natural completion. `StopAndReset` cancels playback without emitting completion. `EffectView` removes listeners before cleanup and rejects callbacks retained from previous pooled uses. Temporary shell disable stops playback without reparenting children inside Unity's hierarchy callbacks; enabling it again starts a fresh playback.
- `EffectVisual` has been removed. The four current impact prefabs use `AnimationEffectVisual` with explicit clip references and non-looping impact clips. The unrelated legacy component on IceProjectile was removed; projectile animation continues through its existing AnimatorController.
- `CombatSpawner` and `CombatAssetsSO` still select child prefabs. A visual prefab must have an `IEffectVisual` implementation on its root. `CombatSpawner.SpawnEffect` prepares the inactive shell, restores the visual's authored local transform and lets shell activation begin playback. No code in the combat spawner needs to distinguish animation from particles.

## Gameplay effects

- Sprite feedback belongs to `CharacterView` for both player and enemy. `CharacterControllerBase` implements the separate `ICharacterFeedbackSource` interface and emits hit/status events; the view subscribes for the current spawn and selects colors with a switch. `EffectManager` reports successful status application/removal through the character to its controller. Poison is purple, burn orange and slow ice blue. Concurrent statuses blend together; multiple instances of the same status keep its color until the last instance is removed. Refreshing an existing timed effect does not add another color instance.
- `CharacterView` retains each renderer's authored color and alpha. Accepted damage, including shield-only damage and direct HP loss, applies a brief 22% blend toward white over the current status tint. Expiry restores the current status color. Disable cancels the flash, while death/despawn/destroy remove listeners, cancel delayed work and restore original colors. The shared `Character.prefab` exposes tint colors, blend strengths and hit duration. `PlayerManager` no longer owns sprite colors or flash tasks; `EnemyCombatFeedback` only handles sprite death playback and Animator restoration.

- `ShootingSkill` stores `[SerializeReference] List<IGameplayEffect>`. Expand Effects, add an entry and choose `SlowEffect`, `BurnEffect` or `PoisonEffect` in the skill inspector. Each selected object contains configuration only.
- `ProjectileSpawnData` carries those configurations plus the source effect-hit stat. The bullet keeps no skill/source-character reference. On an accepted damage hit it calls `EffectManager.Apply(configuration, target, sourceTeam, effectHit)` directly; there is no combat event hub. Other hit producers, such as a future area skill, use the same method.
- `EffectManager` checks spawn identity, team, chance and resistance, then rents an `EffectRuntime`. Reapplying the same timed configuration object to the same target refreshes duration without creating another runtime or resetting periodic cadence. Separate configuration entries remain independent. Each slow runtime owns a percentage MoveSpeed modifier; slows add together and final speed is clamped at zero.
- Configuration types derive from `GameplayEffectData`; running behaviors derive from `EffectRuntime`, which owns `Apply`, `Tick` and `Remove`. Slow-specific modifier ownership lives in `SlowEffectRuntime`; damage behavior lives in `DamageOverTimeEffectRuntime`. Duration and interval accumulation are calculated by the shared `TimerJob`; runtime Tick receives the number of due ticks.
- `ClassPool<T>` wraps Zenject `MemoryPool<T>` for plain C# objects. `EffectRuntimePool` registers pools by runtime type. The installer preallocates 16 slow runtimes and 32 periodic-damage runtimes; pools expand when necessary. Burn and poison can reuse the same runtime type while remaining separate configurations.
- `EffectManager` has no per-frame tick. It receives timer events on the main thread, uses dictionaries to find reapplications and per-target groups for pause/cleanup, and removes runtimes by swapping the final list element. Group lists are reused. Returns are deferred until the current effect operation finishes, so synchronous damage/stat callbacks cannot recycle a runtime while it is still executing. Removal clears modifiers; reset clears target/configuration references before returning to the pool.
- `CharacterView` directly asks `EffectManager` to clear effects on death, destruction and `ClearSpawn`, and pauses timers on temporary disable. `FrostAuraSkill` applies a maintained `SlowEffectRuntime` on entry and removes its versioned handle on exit, pause, data replacement or disposal. Maintained applications create independent runtimes even for a shared configuration; aura slow keeps its guaranteed application behavior. Target identity and handle versions prevent effects from crossing pooled lifetimes.
- Gameplay duration is independent of VFX lifetime. Periodic damage is a fixed `damagePerTick` chosen in each skill and goes through `ReceiveDamage`, including shield absorption. Sample burn uses 2 damage each second for 3 seconds, poison uses 2.5 each second for 4 seconds, and slow reduces speed by 30% for 2 seconds. These periodic values match the old multiplier-based assets at source damage 10; future character damage changes no longer scale them implicitly. Application chance still considers effect hit/resistance when enabled.
- Sample skill YAML now embeds managed effect configurations. The old effect SO assets/classes remain as unused source data; they are no longer applied by the gameplay pipeline.
- Adding an effect requires a serializable configuration and runtime behavior. Register a pool in `GameSceneInstaller` and `EffectRuntimePool` only when introducing a new runtime type. The inspector discovers new concrete serializable configurations automatically.

The previous `ShootingDataSO`, pattern assets, per-projectile assets, pattern/flight/hit factories and separate projectile runtime are removed. The unused homing prefab is also removed; homing uses the same bullet shell.

Skill upgrades, permanent skill progression and selection UI are not implemented. Character/EXP level progression remains in the existing level services.
